# Locked-Phone Timer Makes Expo the Answer

Ivan should build the app with **Expo (React Native), compiled in the cloud by EAS Build and installed on his iPhone through ad hoc internal distribution**, because the single requirement a home-screen PWA cannot satisfy on iOS is a rest-timer alert on a locked phone: WebKit deliberately freezes JavaScript when the screen locks, offers no Vibration API and no client-side scheduled notifications, so the only PWA workaround is a server-sent Web Push at the deadline. The native route costs the **99 USD/year Apple Developer Program** and nothing more (EAS's free plan gives 15 iOS builds a month), needs no Mac at any step, and delivers the two features every praised tracker now has: an OS-scheduled local notification with a custom sound, and, uniquely among no-Mac routes, a Lock Screen/Dynamic Island Live Activity written in JavaScript through `expo-widgets` (Expo SDK 56+). Store data in `expo-sqlite` via Drizzle, seed exercises from **yuhonas/free-exercise-db (public domain, images included)**, map its 17 muscle tags through Liftosaur's published 39-muscle-to-11-body-part table, and give every exercise a Hevy-style type (weighted-bodyweight for belt dips, unilateral for the one-arm machine extension). Use evidence-based defaults: **180 s rest on heavy compounds, 120 s on compound hypertrophy work, 60–90 s on isolation**; add 2.5 kg upper / 5 kg lower when a rep range tops out; Brzycki or Epley e1RM only from sets of 10 reps or fewer, computed on total system load (bodyweight plus belt weight) for dips; primary muscle counts 1.0 and secondary 0.5 toward weekly sets. For body-part ranking, do **not** copy Strength Level (its terms forbid replicating its standards); build a clean-room engine from public formulas (Wilks, DOTS, IPF GL, an allometric exponent of 0.55–0.67), Symmetric Strength's openly served lift-ratio table and muscle-involvement matrix, and OpenPowerlifting's CC0 data, with a time-stamped, editable bodyweight as the normaliser and height deliberately kept out of the score. Parse Strong's export by sniffing the delimiter (classic comma layout versus the 6.2.4+ semicolon layout), reading `Set Order` for W/D/F tags and skipping `Rest Timer` pseudo-rows. The two largest unknowns, whether `expo-widgets` can render a self-updating countdown and which columns Strong's `Rest Timer` rows populate, are each testable in an afternoon and should be checked before any other code is written.

## Only a native build wakes a locked iPhone, and Expo is the cheapest native route from Windows

The requirement that decides the platform is the rest timer. A home-screen web app is now trivially installable: Safari 26 opens every site added to the Home Screen as a web app with no installability requirements at all ([WebKit](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)), installed web apps are exempt from the seven-day script-storage purge because they keep their own days-of-use counter ([WebKit](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)), and since iOS 17 an origin may use up to 60% of disk with `persist()` granted heuristically to home-screen apps ([WebKit](https://webkit.org/blog/14403/updates-to-storage-policy/)). None of that helps once the phone goes in a pocket. An Apple engineer confirmed in March 2025 that JavaScript execution is intentionally halted when web content is backgrounded and that developers cannot override it; Apple's own advice is to store an end timestamp and recompute on return ([Apple Developer Forums](https://developer.apple.com/forums/thread/777860)). The Vibration API is unsupported in every iOS Safari release through 27.2 ([caniuse](https://caniuse.com/vibration)), Notification Triggers never shipped in WebKit, and a developer who tried in September 2026 concluded that only a server-sent push can wake a locked phone ([spotterai PR #39](https://github.com/Ray-Shaw06/spotterai/pull/39)). Two PWA gym projects hit exactly this wall in the week of the research: one whose timer ends silently on a locked iPhone because iOS reclaims the web view ([programme-12-semaines #79](https://github.com/Simon0687/programme-12-semaines/issues/79)), and one that bolted on Upstash QStash (1,000 free publishes a day) to schedule a Web Push at the deadline with HMAC cancel tokens ([spotterai PR #39](https://github.com/Ray-Shaw06/spotterai/pull/39)). Web Push from an installed web app does reach the Lock Screen and a paired Apple Watch ([WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)), but it needs an always-on backend, VAPID keys, and connectivity at the exact moment a rest ends, which gyms do not reliably offer. Screen Wake Lock finally works in installed web apps from iOS 18.4 ([web.dev](https://web.dev/blog/screen-wake-lock-supported-in-all-browsers)), so the honest PWA experience is "keep the screen on and beep while visible", which is a step down from what Strong already gives Ivan. One note flags a contradiction worth naming: the MagicBell PWA guide still claims web push is unavailable in the EU and that storage is capped at 50 MB ([MagicBell](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)), but Apple reversed the EU web-app removal on 1 March 2024 ([9to5Mac](https://9to5mac.com/2024/03/01/apple-home-screen-web-apps-ios-17-eu/)) and the WebKit storage post above supersedes the 50 MB figure. The PWA remains a valid zero-cost fallback only if Ivan accepts Wake-Lock-only timing.

The Expo route removes the problem at the operating-system level. Both `eas build` and `eas submit` run on Windows, and TestFlight internal testing needs no review ([Expo docs](https://docs.expo.dev/submit/testflight/)); the hard prerequisite is the Apple Developer Program at **99 USD a year, billed in local currency where available** ([Apple](https://developer.apple.com/help/account/membership/program-enrollment/)). EAS's free plan gives **15 iOS builds a month on a low-priority queue with a 45-minute timeout**, with waits that can exceed 90 minutes at peak; the Starter plan is 19 USD a month with 45 USD of build credit and iOS medium-worker builds priced at 2 USD each ([Expo pricing](https://expo.dev/pricing); [Expo FYI](https://github.com/expo/fyi/blob/main/eas-build-queues.md)). For one phone, ad hoc internal distribution beats TestFlight: `eas device:create` registers the iPhone's UDID once and EAS hands back an install URL ([Expo docs](https://docs.expo.dev/build/internal-distribution/)), and an ad hoc profile stays valid for a year ([Apple Developer Forums](https://forums.developer.apple.com/thread/115245)), whereas TestFlight builds expire 90 days after upload ([Expo docs](https://docs.expo.dev/submit/testflight/)), which means four re-uploads a year instead of one. JavaScript-only changes can ship through EAS Update without consuming build quota. The rest timer then becomes a textbook local notification: Apple's system delivers them whether or not the app is running ([Apple](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/SchedulingandHandlingLocalNotifications.html)), `expo-notifications` schedules with a `TIME_INTERVAL` or `DATE` trigger and bundles custom sounds through its config plugin ([Expo docs](https://docs.expo.dev/versions/latest/sdk/notifications/)), and iOS keeps the 64 most recently scheduled pending notifications, which is irrelevant for one active timer ([flutter_local_notifications](https://pub.dev/packages/flutter_local_notifications)). The lock-screen countdown comes from `expo-widgets`: **iOS widgets and Live Activities are stable in Expo SDK 56**, authored as React components with no SwiftUI, with Continuous Native Generation creating the widget extension target and App Group ([Expo blog](https://expo.dev/blog/ios-widgets-and-live-activities-in-expo)); the package is iOS-only, requires a development build rather than Expo Go, and exposes `start()`, `update()` and `end()` for the activity lifecycle ([Expo docs](https://docs.expo.dev/versions/latest/sdk/widgets/)). Apple's ActivityKit renders countdowns with `Text(timerInterval:)`, lets an activity run up to eight hours, and, since watchOS 11, mirrors it into the Apple Watch Smart Stack with no watch app at all ([Apple](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)). Two caveats are unresolved in the notes and must be tested on day one: the `expo-widgets` docs do not say whether a self-updating countdown equivalent to `timerInterval` exists in the JS component set (the archived Software Mansion `expo-live-activity` had one), and a 2024 Expo issue reported scheduled local notifications not arriving in the background under one trigger configuration, closed as outdated without a root cause ([expo/expo #28027](https://github.com/expo/expo/issues/28027)). A Live Activity also does not end itself when the timer reaches zero, so the app must call `end()` explicitly ([Apple Developer Forums](https://developer.apple.com/forums/thread/759250)).

Flutter and Capacitor reach the same OS features but at higher cost in Swift. Codemagic gives **500 free macOS M2 minutes a month** with a 120-minute build cap and 0.095 USD per minute beyond ([Codemagic pricing](https://codemagic.io/pricing/)), and its automatic code signing creates the certificate and profile through the App Store Connect API without a Mac ([Codemagic](https://blog.codemagic.io/automatic-code-signing-for-ios-that-doesnt-require-a-mac/)). GitHub Actions macOS runners cost 0.062 USD a minute ([GitHub](https://docs.github.com/en/billing/reference/actions-runner-pricing)), and because macOS minutes count ten-fold against the 2,000 free minutes of a private repo, a free account gets roughly 200 macOS minutes a month, or unlimited standard runners on a public repo ([GitHub](https://docs.github.com/en/billing/managing-billing-for-your-products/about-billing-for-github-actions); [dev.to](https://dev.to/maclessdev/github-actions-free-macos-minutes-explained-33p7)). Their notification plugins are equivalent to Expo's (`flutter_local_notifications` `zonedSchedule`, Capacitor Local Notifications `at`) ([pub.dev](https://pub.dev/packages/flutter_local_notifications); [Capacitor](https://capacitorjs.com/docs/apis/local-notifications)), but a Live Activity requires a hand-written ActivityKit widget extension, and an open-source Flutter tracker records that this missing lock-screen timer was requested twelve times and cost it a lifetime subscriber to Hevy ([heart-of-yours #133](https://github.com/kit-g/heart-of-yours/issues/133)). Without Xcode, authoring and debugging that Swift from Windows is impractical. Capacitor is only interesting as an upgrade path if Ivan starts with a PWA and later wraps it. Sideloading with a free Apple ID is a false economy: SideStore can hold only three apps at once with a seven-day expiry and ten app IDs a week ([SideStore FAQ](https://docs.sidestore.io/docs/faq)), Sideloadly and AltStore need the non-Store iTunes and iCloud on Windows and a PC or daemon to re-sign weekly ([AltStore](https://faq.altstore.io/altstore-classic/how-to-install-altstore-windows); [Sideloadly](https://sideloadly.io/)), and the .ipa still has to be built in the cloud, so the free ID adds upkeep without removing the pipeline. PWABuilder only emits an Xcode project meant for a Mac ([PWABuilder](https://blog.pwabuilder.com/posts/publish-your-pwa-to-the-ios-app-store/)).

The supporting libraries follow from the choice. `expo-sqlite` with Drizzle ORM is described as the smoothest path for a new Expo project, while `op-sqlite` is faster but needs a native build ([React Native Relay](https://reactnativerelay.com/article/building-offline-first-react-native-apps-2026-expo-sqlite-drizzle-orm-sync-strategies); [Kernel Daily](https://kerneldaily.com/articles/expo-sqlite-vs-op-sqlite/)); since widgets already force a development build, either works, and the volumes here (a few thousand sets a year) will never stress `expo-sqlite`. For charts, `react-native-gifted-charts` runs on `react-native-svg` alone, whereas Victory Native XL renders through Skia and Reanimated and requires the dev build Ivan will have anyway ([PkgPulse](https://www.pkgpulse.com/guides/victory-native-vs-react-native-chart-kit-vs-echarts-rn-2026); [victory-native-xl](https://github.com/FormidableLabs/victory-native-xl)). For data safety, iCloud Backup includes device data that is not otherwise synced to iCloud ([Apple Support](https://support.apple.com/en-us/108771)); the note is candid that inclusion of an app's Documents folder is inferred from that wording rather than stated explicitly, and warns that a SQLite database in WAL mode can fail to open after a restore if the `-wal` file is missing, so the app should checkpoint before any backup or export ([Apple Developer Forums](https://developer.apple.com/forums/thread/704859)). A one-tap JSON export through the iOS share sheet is the only backup the user can see and verify, and should exist from the first build. The developer reports the researchers could reach (Reddit was blocked for the crawler) cluster the same way: the author of a personal Expo gym logger chose SQLite for offline logging and warns that Expo Go does not support iOS background tasks ([dev.to](https://dev.to/jjpark987/building-a-gym-logging-app-3c9c)), while every web-based project ended up either adding a push backend or accepting a screen-on timer.

## Rest 2–3 minutes on compounds, add 2.5 kg when the range tops out, trust e1RM only below 10 reps

The rest-interval evidence has moved decisively away from the old "30–60 seconds for hypertrophy" advice. A 2024 Bayesian meta-analysis of nine studies found no appreciable hypertrophy difference once rest exceeds about 90 seconds and recommends resting longer than 60 seconds, explicitly contradicting NSCA's 30–90 second guidance ([Singer et al. 2024](https://www.frontiersin.org/journals/sports-and-active-living/articles/10.3389/fspor.2024.1429789/full)). For strength, the 2018 systematic review concludes that trained lifters need rests longer than two minutes to maximise gains while untrained lifters do fine with 60–120 seconds ([Grgic et al. 2018](https://europepmc.org/article/MED/28933024)), and the underlying RCT in 21 trained men found three-minute rests produced significantly greater squat and bench 1RM gains and anterior-thigh growth than one-minute rests ([Schoenfeld et al. 2016](https://europepmc.org/article/MED/26605807)). The 2014 review that first dismantled the hormonal argument for short rests ([Henselmans & Schoenfeld 2014](https://europepmc.org/article/MED/25047853)) and the ACSM position stand's 3–5 minutes for 1–6 RM loads and 1–2 minutes for 6–12 RM work ([ACSM 2009](https://europepmc.org/article/MED/19204579)) bracket the same range. Strong's factory default of 2:00 for every exercise, with separate warm-up and working durations ([Strong Help](https://help.strongapp.io/article/231-rest-timer)), and Hevy's 5-second-to-5-minute picker in 15-second steps ([Hevy](https://www.hevyapp.com/features/workout-rest-timer/)) show what users are accustomed to. The recommended defaults, stored per exercise and overridable per template row, are **180 s for heavy compound sets of six reps or fewer (range 120–300), 120 s for compound work in the 6–15 rep zone (90–180), 90 s for machine and isolation work (60–120), and 60 s for small-muscle isolation such as abs, calves, rear delts and forearms**. One internal tension deserves flagging: the training-science note also proposes 45 s for the smallest muscles, citing Renaissance Periodization's 15-second-to-2-minute range for rear delts ([RP](https://rpstrength.com/blogs/articles/rear-delt-hypertrophy-training-tips)), while the same note says never to default below 60 s for growth-oriented sets on the strength of Singer 2024; the meta-analysis outranks the coaching guide, so 60 s should be the floor and 45 s a manual override. For Ivan's Push day that yields 180 s after each weighted-dip set, 120 s after incline dumbbell press, and 60–90 s after the one-arm triceps extension, with the timer for a unilateral exercise starting after the second arm rather than after each side. Because the evidence describes minimum rest, the timer should be treated as a floor that the lifter may exceed, not an alarm that penalises waiting.

Progression should default to double progression with equipment-aware increments. The method fills a rep range on every set before adding the smallest available load, so 3 sets of 8–12 at 60 kg advance to 62.5 kg only when all three sets reach 12, after which reps typically fall back to 10, 9 and 8 ([Alpha Progression](https://alphaprogression.com/en/glossary/double-progression)). The NSCA "2-for-2" rule adds weight when the lifter exceeds the target by two reps on the last set in two consecutive workouts, with increments of roughly 1–2 kg upper and 2–5 kg lower body for less-trained lifters and 2–5+ kg and 5–7+ kg for more-trained ones, or 2.5–10% relative jumps ([PT Pioneer](https://www.ptpioneer.com/personal-training/certifications/nsca-cscs/cscs-chapter-17/)), and the ACSM stand recommends 2–10% increases once the current load can be lifted for one or two extra reps on consecutive sessions ([ACSM 2009](https://europepmc.org/article/MED/19204579)). Popular programs converge on **+2.5 kg for upper-body barbell lifts and +5 kg for squats and deadlifts**, with a 10% deload after three consecutive failures ([StrongLifts](https://stronglifts.com/stronglifts-5x5/progress/); [Lift Vault PPL](https://liftvault.com/programs/strength/metallicadpa-ppl-template/)), and GZCLP's cascade (5×3 to 6×2 to 10×1, then restart at about 85% of a new max) is the cleanest stall-handling rule if Ivan ever wants linear progression on a barbell lift ([Massiv](https://massiv.app/blog/gzclp-progression/)). The app's suggestion logic should therefore be: all sets at the top of the range, add the exercise's minimum step (2.5 kg on a belt or barbell, 2 kg per hand on dumbbells, one pin or a 2.5 kg add-on plate on a stack); any set below the bottom of the range for two or three sessions, hold or reduce 5–10%; otherwise keep the load and add reps. A percent guard matters at light loads: 30 to 32.5 kg is an 8.3% jump, above the 2.5–5% upper-body guidance, so the app should prefer 1.25 kg micro-plates or a wider range there, and it should expect roughly seven or eight reps after such a jump by inverting Epley. If Ivan logs RPE, the validated rule is to change load by about 2% for every 0.5 RPE of deviation from the target ([Helms et al. 2018](https://www.frontiersin.org/journals/physiology/articles/10.3389/fphys.2018.00247/full)), with targets of roughly 7–8 for hypertrophy work and 9 for heavy strength sets, bearing in mind that lifters over-estimate reps in reserve by about five reps when far from failure ([MASS](https://massresearchreview.com/2023/05/22/rpe-and-rir-the-complete-guide/)). Hypertrophy improves as sets approach failure while strength gains are flat across a wide RIR range ([Robinson et al. 2024](https://europepmc.org/article/MED/38970765)), and the only deload RCT found a full week off cost lower-body strength without adding hypertrophy ([Coleman et al. 2024](https://europepmc.org/article/MED/38274324)), so deloads should be reduced-volume weeks triggered by stalls, not calendar-fixed rest weeks. None of this is validated head-to-head in recreational lifters; increments for dumbbells and machines are equipment conventions rather than experimental findings.

The estimated 1RM needs three rules: which formula, which sets, and what load counts. Brzycki (w × 36 ÷ (37 − r)) is what Strong uses, and Strong itself warns the estimate is unreliable above 12 reps ([Strong Help](https://help.strongapp.io/article/133-1rm)); Epley is w × (1 + r ÷ 30), and the two are identical at 10 reps and diverge either side ([Wikipedia](https://en.wikipedia.org/wiki/One-repetition_maximum)). In 70 subjects, a 5RM predicted bench 1RM with R² = 0.993, Brzycki was among the most accurate equations for bench but under-estimated leg press, and no more than 10 reps should feed a linear equation ([Reynolds et al. 2006](https://www.unm.edu/~rrobergs/478RMStrengthPrediction.pdf)); in 103 women the linear Brzycki and Lander equations over-estimated wildly when 2–30-rep sets were allowed (mean error 26.7% with a standard deviation over 100 percentage points) but came within ±5% once sets were restricted to 10 reps or fewer ([Mayhew et al. 2008](https://www.unm.edu/~rrobergs/478PredictionAccuracy.pdf)). Secondary summaries of LeSuer 1997 report that every equation under-predicts the deadlift, by roughly 8–10% ([OneRepMaxCalculators](https://onerepmaxcalculators.com/guides/one-rep-max-basics/how-accurate-are-1rm-calculators/)), and Hevy sidesteps formulas entirely with a fixed percentage table that floors at 50% above 30 reps ([Hevy Help](https://help.hevyapp.com/hc/en-us/articles/36954464726167-Understanding-Your-Estimated-One-Rep-Max-1RM-in-Hevy)). The notes disagree mildly on the default: the training-science and standards notes lean to Epley or Wathan, while Strong's records are Brzycki. **Use Brzycki for sets of 10 reps or fewer** so that Ivan's imported PR history stays continuous with what Strong showed him and because it is among the most accurate for bench at 5RM; show Epley as a secondary figure; flag any estimate from a set of more than 10 reps as low confidence and exclude it from ranking; store the rep count beside every e1RM so charts can filter to comparable rep ranges. A 2026 preprint on 303,494 Fitbod sets offers a useful refinement: the conversion factor rises with load (roughly 8 at 10 kg, 17 at 70 kg, 20 at 150 kg), so classical formulas under-value each rep on light dumbbell and cable movements by up to a fifth ([Marzagao 2026](https://arxiv.org/abs/2603.17495)); it is not validated against measured maxes, so it belongs behind an "experimental" toggle for isolation lifts, and the practical consequence is that e1RM on the one-arm triceps extension is a within-exercise trend metric only.

Weighted dips and the unilateral machine extension need explicit load models. For pull-ups, chin-ups and dips the quantity to feed a formula is total system load, bodyweight plus belt weight, with the belt-equivalent recovered by subtracting bodyweight afterwards; ExRx suggests 90.6–92.8% of bodyweight if precision matters ([ExRx](https://exrx.net/WeightTraining/Bodyweight)), and consumer calculators simply add 100% of bodyweight, so an 80 kg lifter doing +20 kg for 5 becomes about 117 kg total, or +37 kg added ([StrengthCalculator](https://strengthcalculator.org/pull-up-calculator)). Strength Level keys its dip and pull-up standards on added weight, negative for assistance ([Strength Level](https://strengthlevel.com/strength-standards/dips/kg)), and Symmetric Strength converts the entered total minus bodyweight through a fitted polynomial ([Symmetric Strength](https://symmetricstrength.com/static/res/libs.js)); the physics agree, so the app stores `added_kg`, computes on `bodyweight + added`, and displays the added figure. This forces a bodyweight time series: log it per session or interpolate, using the weight at which the lift was performed rather than a nominal one. For unilateral work there is no validation literature at all; treat the per-limb load as the weight, compute per side with the same formula, never sum sides, and keep it as a trend. Dumbbells are logged per hand as Strong does, with Strong's "count dumbbells twice" volume toggle mirrored as a per-exercise flag ([Strong Help](https://help.strongapp.io/article/101-how-are-dumbbell-exercises-counted)); Strength Level's dumbbell rows are per single dumbbell including the roughly 2 kg bar ([Strength Level](https://strengthlevel.com/strength-standards/incline-dumbbell-bench-press/kg)). Worked for an 80 kg × 5 set: Brzycki 90.0 kg, Epley 93.3 kg, Wathan 93.6 kg, Hevy's table 89.9 kg.

Weekly volume per muscle should be counted fractionally against a 10–20 set band. The dose-response meta-analysis found each additional weekly set adds about 0.37% growth, with fewer than 5, 5–9 and 10+ weekly sets yielding roughly 5.4%, 6.6% and 9.8% ([Schoenfeld et al. 2017](https://europepmc.org/article/MED/27433992); [Built With Science](https://builtwithscience.com/fitness-tips/how-many-sets-per-muscle-group-per-week/)); strength shows the same graded relationship ([Ralston et al. 2017](https://europepmc.org/article/MED/28755103)); **12–20 weekly sets is proposed as the optimum for trained men** ([Baz-Valle et al. 2022](https://europepmc.org/article/MED/35291645)); four weekly sets per muscle is the time-efficient floor ([Iversen et al. 2021](https://europepmc.org/article/MED/34125411)); and the 2025 meta-regression of 67 studies found that counting indirect sets as 0.5 fits the data best and that diminishing returns are far steeper for strength than for size ([Pelland et al.](https://europepmc.org/article/MED/41343037)). Hevy's own guidance uses the same rule of thumb, one set for the primary muscle and half a set for each secondary ([Hevy](https://www.hevyapp.com/how-many-sets/)). The app should count only working sets (Strong excludes warm-ups from all charts, which Ivan is used to ([Strong Help](https://help.strongapp.io/article/166-set-tags))), credit the primary muscle 1.0 and each secondary 0.5, and show a band of 10–20 fractional sets with a floor alert at 4. For ceilings, the notes warn that the widely copied Renaissance Periodization tables are stale: the 2023–24 republication lowered many landmarks, giving chest MEV 4–6 and MRV 16–24, quads MRV 14–18, triceps MRV 16–20, hamstrings only 8–14, front delts 8–12, and biceps 20–26 ([RP chest](https://rpstrength.com/blogs/articles/chest-training-tips-hypertrophy); [RP quads](https://rpstrength.com/blogs/articles/quad-training-tips-hypertrophy); [RP triceps](https://rpstrength.com/blogs/articles/triceps-hypertrophy-training-tips); [RP hamstrings](https://rpstrength.com/blogs/articles/hamstring-hypertrophy-training-tips); [RP front delts](https://rpstrength.com/blogs/articles/front-delt-hypertrophy-training-tips); [RP biceps](https://rpstrength.com/blogs/articles/bicep-hypertrophy-training-tips)), whereas third-party compilations still circulate older numbers such as chest MEV 6–8 and quads MRV 20–24. RP's back landmarks exist only as an image and could not be extracted, so back inherits the generic 10–20 band.

## Rank body parts clean-room: public formulas, an involvement matrix, and no height term

The obvious source of standards is the one Ivan cannot embed. Strength Level defines its five tiers as population percentiles, Beginner stronger than 5% of lifters, Novice 20%, Intermediate 50%, Advanced 80%, Elite 95%, from a database of 195.5 million lifts by 27.9 million users across 287 exercises, with tables in 5 kg bodyweight rows and a model that is linear in bodyweight at a fixed level ([Strength Level](https://strengthlevel.com/about); [Strength Level](https://strengthlevel.com/strength-standards/bench-press/kg)). Its terms prohibit replicating or creating derivative versions of its calculators or standards and any systematic copying or scraping ([Strength Level](https://strengthlevel.com/terms-and-conditions)), and ExRx's Kilgore tables cannot be republished without written permission ([ExRx](https://exrx.net/Questions/Content)). The standards note judges that typing a handful of rows into a private, never-distributed app is low-risk while shipping them would breach the terms; that is Ivan's call, and this report treats the clean-room path as the default. The clean-room ingredients are all public: OpenPowerlifting waives copyright on every meet-data CSV and publishes its formula code under AGPLv3+ ([OpenPowerlifting](https://gitlab.com/openpowerlifting/opl-data/-/raw/main/README.md)); the Wilks, DOTS and IPF GL coefficients are federation-published constants ([Wikipedia](https://en.wikipedia.org/wiki/Wilks_coefficient); [OpenPowerlifting dots.rs](https://gitlab.com/openpowerlifting/opl-data/-/raw/main/crates/coefficients/src/dots.rs); [OpenPowerlifting goodlift.rs](https://gitlab.com/openpowerlifting/opl-data/-/raw/main/crates/coefficients/src/goodlift.rs)); and Symmetric Strength documents its method on its About page and serves its scoring code publicly, though no licence statement was found, so the method and constants should be reimplemented rather than the code copied, which is what the MIT-licensed Body-Assessment project does ([Symmetric Strength](https://symmetricstrength.com/about); [danmcne/Body-Assessment](https://github.com/danmcne/Body-Assessment)). `liftmath` (GPL-3.0) shows the other clean-room pattern, bucketing a user's DOTS against OpenPowerlifting per-lifter bests into 99 percentile breakpoints for offline use ([munzzyy/liftmath](https://github.com/munzzyy/liftmath)); copying its code would pull the app under GPL, so use it as a design reference only.

| Strength Level | 287-exercise percentile tables, 5 kg rows, five tiers | Terms forbid replication, derivative calculators, systematic copying | Private calibration reference at most; never embed |
| Symmetric Strength | Lift-ratio table, dip/chin polynomials, 22-muscle involvement matrix, tier cut-offs, age quadratics | Method public; served JS has no licence (copyrighted by default) | Reimplement the method and constants |
| ExRx | Kilgore tables for four to six barbell lifts | No republication without written permission | Private reference only |
| OpenPowerlifting | Full meet database; Wilks/DOTS/GL/McCulloch code | Data CC0; code AGPLv3+ | Derive SBD percentiles from the CSV; re-type the constants |

| Body-Assessment / liftmath | Reimplementations | MIT / GPL-3.0 | Copy MIT freely; GPL as reference only |

The recommended engine follows Symmetric Strength's architecture because it needs no proprietary tables, handles weighted bodyweight lifts natively, and already contains a per-muscle aggregation. Each lift is scored as one quarter of the age-adjusted Wilks score of the powerlifting total it implies ([Symmetric Strength](https://symmetricstrength.com/about)). The implied total comes from a published ratio table: a male deadlift is 0.396825 of the total, back squat 0.87 and bench 0.65 of the deadlift share, front squat 0.8 of squat, incline bench 0.82 of bench, overhead press 0.65 of bench, Pendlay row 0.53 of deadlift, pull-up 0.95 of chin-up; dips and chin-ups use fourth-order polynomials in the added load in pounds, with the male dip polynomial 1.68064e-10·l⁴ − 1.2946e-7·l³ + 3.71905e-5·l² − 0.00499168·l + 0.566576 ([Symmetric Strength](https://symmetricstrength.com/static/res/libs.js)). The Wilks coefficient for a **73 kg man is 0.7264** (DOTS 0.7301; IPF GL raw denominator 676.4), computed from the published polynomials, and the tier cut-offs are score ≥125 World Class, ≥112.5 Elite, ≥100 Exceptional, ≥87.5 Advanced, ≥75 Proficient, ≥60 Intermediate, ≥45 Novice, ≥30 Untrained ([Symmetric Strength](https://symmetricstrength.com/static/res/libs.js)). Worked for Ivan: a **+40 kg weighted dip (113 kg total) scores about 60.9, Intermediate**; a +30 kg chin-up scores 65.3; a 90 kg bench, 120 kg squat, 140 kg deadlift and 55 kg press score 63.4, 63.1, 64.1 and 59.6, for an overall 63.1 with a symmetry of 96.3. Aggregation is the part most apps get wrong and Symmetric Strength gets right: the overall score averages the best lift in each of five movement categories (squat, floor pull, pull-up, horizontal press, vertical press) precisely so that being elite at bench, incline and dip does not count horizontal pressing three times ([Symmetric Strength](https://symmetricstrength.com/about)). Each muscle group is a weighted average of the lifts that involve it using published 0–10 involvement weights (bench: lower chest 10, upper chest 8, triceps 8, front delts 6; dip: lower chest 10, triceps 8, upper chest 6, front delts 6, lower traps 6; pull-up: lats 10, and 6 each for mid/lower traps, rear delts, rotator cuff, biceps, forearms, abs), the weights are cubed in the average so a muscle's score is dominated by the lifts that load it most, and a muscle stays grey until the sum of cubed weights reaches 50, which means at least one lift with involvement 4 or more ([Symmetric Strength](https://symmetricstrength.com/static/res/libs.js)). Balance is simply 100 minus the population variance of the lift scores, with the site's own warning that a lower symmetry score is not necessarily worse given individual leverages ([Symmetric Strength](https://symmetricstrength.com/about)). Mapping those 22 muscles to the app's 11 body parts is a one-time join (upper and lower chest to chest; lats, spinal erectors and traps to back; front, side and rear delts to shoulders; and so on).

Bodyweight enters twice and height enters nowhere. Every federation formula takes bodyweight and sex only; the theoretical allometric exponent is 2/3, lean young men fit 0.66, adipose subjects fit about 0.45, and fat-free mass with an exponent of 0.76 is the recommended index ([Folland et al. 2008](https://europepmc.org/article/MED/18172672)); the general powerlifting population fits 0.55 while elite lifters fit only 0.35–0.52 by lift, with bench attenuating most ([Montenegro et al. 2026](https://www.frontiersin.org/journals/physiology/articles/10.3389/fphys.2026.1847605/full)); and the classic review recommends 0.67 for force while condemning plain ratio scaling as biased against heavier lifters ([Jaric 2002](https://europepmc.org/article/MED/12141882)). So the app should compute both the familiar ratio (load ÷ bodyweight; a 100 kg bench at 73 kg is 1.37×) and an allometric index (load ÷ 73^0.67 = load ÷ 17.7, so 5.64), and use the Wilks-based score above for tiers. The bodyweight must be the one at which the lift was performed, so the profile holds a time-stamped series and each session takes the nearest reading; Strong's separate `strong_weight.csv` body-measurement export can seed it ([Taper](https://thetaperapp.com/articles/how-to-export-strong-data/)). Height should not modify the score. No published standard uses it; adding height, weight, fat-free mass or girths to a 5RM-based equation did not improve 1RM prediction ([Reynolds et al. 2006](https://www.unm.edu/~rrobergs/478RMStrengthPrediction.pdf)); the one controlled study found that strength normalised to body mass was still biased by height but strength normalised to fat-free mass was not ([Folland et al. 2008](https://europepmc.org/article/MED/18172672)); and while limb proportions demonstrably shift individual lifts (longer reach helps relative deadlift and hurts relative bench, torso girth predicts absolute squat, bench and deadlift), the effects are direction-specific per lift and unquantified as a correction ([Ferland et al. 2020](https://europepmc.org/article/MED/33414873)). The evidence-based use of Ivan's 179 cm is contextual: estimate fat-free mass from bodyweight and body-fat and show FFMI, or explain why a tall lifter's bench lags, never as a multiplier. Age is a multiplier of 1.0 between 23 and 40, with Foster coefficients for juniors and McCulloch coefficients for masters (1.055 at 45, 1.130 at 50) if ever needed ([OpenPowerlifting mcculloch.rs](https://gitlab.com/openpowerlifting/opl-data/-/raw/main/crates/coefficients/src/mcculloch.rs)); Symmetric Strength's quadratic fits reproduce those tables within a percent ([Symmetric Strength](https://symmetricstrength.com/static/res/libs.js)).

Three honest limits shape how the rank should be presented. First, the clean-room populations are harsh: Symmetric Strength says its classifications compare you to strength athletes rather than average gym-goers ([Symmetric Strength](https://symmetricstrength.com/about)), and Barbell Medicine notes that recreational lifters after one or two years (squat 1.0–1.5×, bench 0.7–1.1×, deadlift 1.25–1.75× bodyweight) sit near the 10th percentile of competitive powerlifters, whose 90th-percentile male ratios are 2.83, 1.95 and 3.25 ([Barbell Medicine](https://www.barbellmedicine.com/blog/strength-standards/); [van den Hoek et al. 2024](https://europepmc.org/article/MED/39060209)). The UI should say "relative to competitive lifters" or relabel the tiers, and a "stronger than X%" sentence is only honest when thresholds are percentile-anchored. Second, coverage is thin exactly where Ivan trains: Symmetric Strength covers 14 barbell and bodyweight lifts and deliberately excludes dumbbells, Hevy ranks only 13 exercises ([Hevy Help](https://help.hevyapp.com/hc/en-us/articles/38001696749335-Strength-Level-Feature-How-Hevy-Compares-Your-Strength-by-Exercise)), and reviewers of Liftoff, which ranks 400 exercises, complain that lesser-used exercises are "very off" ([Liftoff](https://liftoffrank.com/gamified-workout-tracker)). For Ivan's Push day the weighted dip is well covered, the incline dumbbell press has only a Strength Level row (per dumbbell: about 19, 26, 36, 47 and 58 kg at 73 kg, computed by interpolating the site's 70 and 75 kg rows ([Strength Level](https://strengthlevel.com/strength-standards/incline-dumbbell-bench-press/kg))) and a barbell-only 0.82 ratio, and the one-arm machine extension has no standard anywhere. The practical answer is to rank a short list of anchor lifts with published standards, one per body part (weighted dip for chest and triceps, weighted chin-up or pull-up for back and biceps, overhead press for shoulders, squat or leg press for quads, deadlift or RDL for hamstrings and glutes), let body parts inherit through the involvement matrix, and label everything else an estimate. For private calibration, the interpolated Strength Level lines at 73 kg are bench 49, 68, 89, 114 and 141 kg, dip +3, +24, +48, +75 and +104 kg added, pull-up −2, +14, +32, +51 and +72 kg ([Strength Level](https://strengthlevel.com/strength-standards/bench-press/kg); [Strength Level](https://strengthlevel.com/strength-standards/dips/kg); [Strength Level](https://strengthlevel.com/strength-standards/pull-ups/kg)), and the site's headline bodyweight-ratio summaries (0.5×, 1.0×, 1.25×, 1.5×, 2.0× for bench) do not match its own rows (0.68×, 0.93×, 1.22×, 1.56×, 1.93× at 73 kg), so an implementer must store rows, never ratios. Third, the push-pull balance ratios that sound authoritative are not: the only competition-verified ratios are squat 1.5 : bench 1.0 : deadlift 1.73 for median raw men ([Fitness Volt](https://fitnessvolt.com/strength-standards/research/squat-bench-deadlift-ratio)), while overhead press at 60–67% of bench ([StrengthCalculator](https://strengthcalculator.org/overhead-press-calculator)), row at roughly 1:1 with bench ([StrengthCalculator](https://strengthcalculator.org/barbell-row-calculator)) and Poliquin's structural-balance table are coaching opinion, and two versions of Poliquin's numbers circulate that disagree (chin-up 81% versus 87% of close-grip bench, incline 83% versus 91%) ([T-Nation](https://archive.t-nation.com/training/achieving-structural-balance/); [Peter Roberts Coaching](http://www.peterrobertscoaching.com/blog/definitive-guide-to-structural-balance-training)). A balance screen may flag squat:deadlift outside 0.75–1.0 or bench:squat outside 0.55–0.85 as evidence-grade and everything else as opinion-grade. Presentation should follow the documented idiom, a tier label per exercise, a continuous score, and a colour-coded body diagram that stays grey where data are insufficient, which is what Symmetric Strength, Stronger and Fitbod all use ([Stronger](https://www.strongermobileapp.com/strength-score); [Fitbod](https://fitbod.me/blog/muscle-strength/)); no source documents a per-body-part radar chart.

## Embed free-exercise-db, fold 17 muscles into 11 body parts, and reconcile Strong's names against it

Only two open datasets combine a real muscle taxonomy with terms that allow embedding. **yuhonas/free-exercise-db holds 800+ exercises under The Unlicense**, with images served from the repository, was last pushed on 30 August 2026, and gives each record `force`, `level`, `mechanic`, `equipment`, `primaryMuscles`, `secondaryMuscles`, `instructions`, `category` and `images` ([GitHub API](https://api.github.com/repos/yuhonas/free-exercise-db); [README](https://github.com/yuhonas/free-exercise-db)). Its schema enumerates 17 muscle values (abdominals, abductors, adductors, biceps, calves, chest, forearms, glutes, hamstrings, lats, lower back, middle back, neck, quadriceps, shoulders, traps, triceps), 12 equipment values including a single generic "machine" and "cable", and seven categories ([schema.json](https://raw.githubusercontent.com/yuhonas/free-exercise-db/main/schema.json)); the README warns that `force`, `mechanic` and `equipment` are incomplete in some files. It already contains Ivan's Push exercises as "Dips - Chest Version" (chest, with shoulders and triceps secondary), "Incline Dumbbell Press" (chest; shoulders, triceps) and "Cable One Arm Tricep Extension" (triceps, isolation) ([free-exercise-db](https://raw.githubusercontent.com/yuhonas/free-exercise-db/main/exercises/Dips_-_Chest_Version.json); [free-exercise-db](https://raw.githubusercontent.com/yuhonas/free-exercise-db/main/exercises/Incline_Dumbbell_Press.json); [free-exercise-db](https://raw.githubusercontent.com/yuhonas/free-exercise-db/main/exercises/Cable_One_Arm_Tricep_Extension.json)). The wger database is the cross-check: 912 exercise bases and 3,373 translations behind an unauthenticated JSON API, last pushed 25 September 2026, with 15 Latin-named muscles (only nine of which carry an English name), eight coarse categories and twelve equipment values that include "Cable machine" but no generic machine ([wger](https://wger.de/api/v2/exerciseinfo/?limit=1); [wger](https://wger.de/api/v2/muscle/?limit=50)). Its exercise text is Creative Commons per entry, CC-BY-SA 4 by default ([wger](https://github.com/wger-project/wger); [wger](https://wger.de/api/v2/license/)), so copying descriptions triggers attribution and share-alike, while mirroring its names as aliases and its muscle IDs is harmless. Everything else is either encumbered or small: everkinetic is CC-BY-SA-4.0 ([GitHub API](https://api.github.com/repos/everkinetic/data)); hasaneyldrm's 1,324-exercise set has MIT text but its GIFs are Gym visual's, shipped at 180 px only, and its NOTICE says cloning the repo is not a licence ([README](https://raw.githubusercontent.com/hasaneyldrm/exercises-dataset/main/README.md); [NOTICE](https://raw.githubusercontent.com/hasaneyldrm/exercises-dataset/main/NOTICE.md)); RepDB's 601 exercises allow in-app use with a visible attribution link but forbid redistribution as a dataset, and are notable for shipping `is_unilateral` and `is_bodyweight` flags ([RepDB](https://github.com/RepDB/exercise-dataset)); rthepen (630 exercises, MIT, a 29-muscle taxonomy and a `tracking_type` field) and Glowupp's Open ExerciseDB (300+, MIT, no media) are single-maintainer 2026 projects ([rthepen](https://github.com/rthepen/workout-database); [Glowupp](https://github.com/Glowupp-app/open-exercisedb)); ExerciseDB sells 1,394 exercises for a one-time 199 or 599 USD ([exercisedb.io](https://exercisedb.io/pricing)); and MuscleWiki's API forbids offline use outright ([MuscleWiki](https://api.musclewiki.com/faq)). For a single-user app, free-exercise-db as the seed with wger names as aliases is the whole answer, and RepDB's laterality flag is worth copying as a convention.

The body-part taxonomy should have three layers so that rankings, volume charts and a future heat map do not require re-tagging. The bottom layer is Liftosaur's 39 anatomical strings and the middle is Hevy's 20 muscle groups; the top is the eleven body parts Ivan asked for. Liftosaur publishes, as code with an inverse map, a `screenMuscleToMuscleMapping` that folds its 39 muscles into exactly eleven screen groups: shoulders (three deltoid heads, infraspinatus, teres major and minor), triceps, back (erector spinae, lats, levator scapulae, three trapezius portions, sternocleidomastoid, splenius), abs (obliques, rectus abdominis, iliopsoas), glutes (gluteus maximus, medius, TFL), hamstrings (plus the three adductors), quadriceps (plus adductor brevis and longus, pectineus, sartorius), chest (both pectoralis heads and serratus anterior), biceps (biceps brachii, brachialis), calves (gastrocnemius, soleus, tibialis anterior) and forearms ([Liftosaur](https://raw.githubusercontent.com/astashov/liftosaur/master/src/models/muscle.ts)). Hevy's API enumerates 20 groups: abdominals, shoulders, biceps, triceps, forearms, quadriceps, hamstrings, calves, glutes, abductors, adductors, lats, upper_back, traps, lower_back, chest, cardio, neck, full_body and other ([hevy-mcp OpenAPI copy](https://raw.githubusercontent.com/chrisdoc/hevy-mcp/main/openapi-spec.json)). The crosswalk from free-exercise-db's 17 tags is therefore mechanical: lats, middle back, lower back and traps fold into back; adductors into quads and abductors into glutes (following Liftosaur); abdominals into abs; neck stays unmapped. The one genuine ambiguity is the trapezius, which Hevy separates, Liftosaur files under back and wger leaves without an English name; the notes recommend back for rows and shrugs and documenting the choice. No peer-reviewed mapping exists; Liftosaur's is a developer convention adopted because it is the only one published verbatim with an inverse. For exercise types, Hevy's eight cover every case Ivan has and give a lossless import target: weight and reps, bodyweight reps, weighted bodyweight, assisted bodyweight, duration, duration and weight, distance and duration, weight and distance ([Hevy](https://www.hevyapp.com/features/custom-exercises/)); the notes flag that two versions of Hevy's API enum circulate with different spellings and equipment lists, so the names should be treated as the app's own, not as a wire format. Alpha Progression's "bodyweight involvement 0–100%" is the only documented mechanism for making dips comparable to barbell lifts and is worth storing as a `bodyweight_factor` per exercise ([Alpha Progression](https://alphaprogression.com/en/blog/alpha-progression-guide)).

Strong's export comes in two layouts, and the importer must sniff which it has. The classic file is comma-delimited with the header `Date,Workout Name,Duration,Exercise Name,Set Order,Weight,Reps,Distance,Seconds,Notes,Workout Notes,RPE`, one row per set, dates like `2020-12-30 18:51:52` with no timezone, durations like `2h 38m`, and no unit column ([StrongAppAnalytics](https://github.com/AlexandrosKyriakakis/StrongAppAnalytics/blob/main/Data/strong.csv); [Taper](https://thetaperapp.com/articles/how-to-export-strong-data/)); a variant puts `Workout Duration` last ([Kinoku](https://kinoku.app/import-format)). Exports from **Strong 6.2.4 onward are semicolon-delimited with quoted fields** and the header `"Workout #";"Date";"Workout Name";"Duration (sec)";"Exercise Name";"Set Order";"Weight (kg)";"Reps";"RPE";"Distance (meters)";"Seconds";"Notes";"Workout Notes"`, which at least one importer rejected outright in September 2026 ([openGym #302](https://github.com/DuarteSantos8/openGym/issues/302)), and which adds one `Rest Timer` row per exercise that a careless importer turns into an empty set ([Kinoku](https://kinoku.app/import-format)). The rules that fall out are: detect the delimiter and the presence of `Workout #`; normalise headers by lower-casing and stripping unit suffixes so `Weight (kg)` yields both the column and the unit; group rows by `Workout #` when present, else by date plus workout name; parse `Duration` as either seconds or space-separated `h`/`m`/`s` segments, which strong2hevy's tests cover for `1h 17m`, `58m` and `6m 30s` ([strong2hevy](https://github.com/criccomini/strong2hevy)); tolerate floating-point artefacts such as `185.00000000000003` ([AJ's blog](https://blog.ayjc.net/posts/strong-app-parsing/)) and decimal commas ([RepStack](https://rep-stack.com/import/strong-csv/)); and ask the unit once when the header is unit-less, since a 2.2× discrepancy after import is the tell-tale of a kg/lb mix-up ([Gript](https://griptapp.com/help/import-from-strong)). `Set Order` is a 1-based integer for normal sets or a letter, W for warm-up, D for drop set, F for failure ([Gript](https://griptapp.com/help/import-from-strong)), so the set index must be taken from row order within the exercise rather than from the column; `Rest Timer` rows are skipped as sets but their value should be harvested to seed each exercise's default rest ([Avex PR #202](https://github.com/antho976/Avex/pull/202)); Strength Journeys also references `Note` rows ([Strength Journeys](https://www.strengthjourneys.xyz/import/strong)). Two gaps are explicit: no source shows a verbatim `Rest Timer` or `Note` data row, so which column carries the seconds is an inference Ivan must confirm by opening his own file, and nothing documents whether pinned notes or template definitions are exported at all (the help centre says exports cannot be re-imported into Strong, and only completed workouts export ([Strong Help](https://help.strongapp.io/article/235-export-workout-data))). Turn "Include Notes" on before exporting, because notes are the one thing that cannot be reconstructed afterwards ([Gript](https://griptapp.com/help/import-from-strong)).

Exercise-name reconciliation is the real work of the import. Strong names exercises as movement plus equipment in parentheses, "Bench Press (Barbell)", "Hip Adductor (Machine)", "Face Pull (Cable)", "Hip Thrust (Bodyweight)", with some names such as "Power Clean" carrying no suffix ([AJ's blog](https://blog.ayjc.net/posts/strong-app-parsing/); [StrongAppAnalytics](https://github.com/AlexandrosKyriakakis/StrongAppAnalytics/blob/main/Data/strong.csv)), and Hevy uses the identical convention, so one alias table serves both. The pipeline copied from strong2hevy and the heart-api design issue is: split on the last " (" into base movement and equipment token; exact-match against an alias table seeded with free-exercise-db names, wger English names and the parenthesised forms; fall back to a token match on base movement plus equipment; and present the leftovers in a review screen whose decisions (use existing, create custom, skip) are persisted as new aliases, with an import-state hash to make re-imports idempotent ([strong2hevy](https://github.com/criccomini/strong2hevy); [heart-api #39](https://github.com/kit-g/heart-api/issues/39)). Ivan's own names will map as "Incline Bench Press (Dumbbell)" to "Incline Dumbbell Press", "Dips" or "Chest Dip" to "Dips - Chest Version", and "Triceps Extension (Cable)" or a custom one-arm name to "Cable One Arm Tricep Extension". No complete list of Strong's roughly 200 built-in names was found anywhere, so the alias table will grow through the review screen. Hevy's own native Strong import, which requires an English-language export and allows one import per account, lost five to ten of about 900 workouts for one user and renamed some workouts ([Hevy Help](https://help.hevyapp.com/hc/en-us/articles/38001424401943-How-to-Import-Strong-App-CSV-Files-and-Export-Your-Data-in-Hevy); [AJ's blog](https://blog.ayjc.net/posts/migrate-strong-hevy-app/)), which is the standard to beat: the app's importer should report every rejected row rather than drop it silently. Because Strong's CSV carries a per-set `Notes` column, the importer can also pre-seed each exercise's pinned note with the most recent non-empty note and ask Ivan to confirm.

## Model templates, machine notes and rest times the way Strong users praise and Hevy users beg for

The UX patterns to keep are the ones users praise in Ivan's current app, and the pain points to remove are documented just as clearly. Strong's template is a blueprint of exercises and sets in which sets cannot be completed and the timer does not run, with a free-tier cap of three templates that is the single most repeated complaint ([Strong Help](https://help.strongapp.io/article/105-about-templates); [JustUseApp](https://justuseapp.com/en/app/464254577/strong-workout-tracker-gym-log/reviews)). Starting a template clones it into a live workout, and on finish Strong offers four options, Update Template, Update Values Only, Update Template and Values, and Keep Original, whose wording the help centre itself admits will be revised to reduce confusion ([Strong Help](https://help.strongapp.io/article/177-update-template)); Hevy's marketing says it asks whether to apply changes, while its reviewers complain that no such save-versus-update choice exists when an exercise was swapped mid-workout ([Hevy](https://www.hevyapp.com/features/gym-routines/); [JustUseApp](https://justuseapp.com/en/app/1458862350/hevy-workout-tracker-gym-log/reviews)), a disagreement between vendor copy and users that the notes flag. The personal app should keep two operations only: "update targets from today" (values) and "replace structure". Where rest time lives is the subtler design point. Strong stores it per exercise globally, which a reviewer complains resets the timer to whatever the last workout used when the same exercise appears in a different template ([Strong Help](https://help.strongapp.io/article/231-rest-timer); [JustUseApp](https://justuseapp.com/en/app/464254577/strong-workout-tracker-gym-log/reviews)), whereas Hevy saves rest periods inside the routine and lets sessions override them ([Hevy](https://www.hevyapp.com/features/workout-rest-timer/)). The synthesis is to store rest on the template-exercise row, seeded from an exercise-level default, with separate warm-up and working durations as Strong does and a zero rest between consecutive drop-set segments as Hevy does ([Hevy](https://www.hevyapp.com/features/workout-set-types/)); PonteFuerte's comparison lists the missing warm-up/working split as a Hevy weakness ([PonteFuerte](https://www.pontefuerteai.com/blog/hevy-vs-strong-vs-pontefuerteai-workout-app-comparison)). The live screen is the de-facto standard grid of Set, Previous, kg, Reps and a check; tapping the set number opens the Warm-up, Drop, Failure menu; checking a set turns the row green, fires a PR badge and starts that exercise's timer ([Strong Help](https://help.strongapp.io/article/166-set-tags); [Hevy](https://www.hevyapp.com/features/track-workouts/)). The Previous column should default to Hevy's "same routine" mode rather than "any workout" ([Hevy Help](https://help.hevyapp.com/hc/en-us/articles/34105442929943-Previous-Workout-Values-Vs-Routine-Values-How-to-Adjust-in-Settings)), because a PPL lifter does the same movement at different rep targets on different days, and target, previous, pre-filled and confirmed values must look visually distinct, the one design rule repeated across sources ([ScreensDesign](https://screensdesign.com/articles/workout-tracker-app-design-examples/)).

The timer implementation is a three-part pattern that every current tracker has converged on. At set completion the app computes an end timestamp, schedules a local notification with a short custom sound at that instant, and renders the countdown from the timestamp so backgrounding costs nothing; skipping or adding 15 s cancels and reschedules; per-exercise defaults fall back to a global one; and the screen is kept awake during a workout ([healthtracker #340](https://github.com/NevinJulian/healthtracker/issues/340)). The sound must come from the notification, not from in-app audio, because "timer doesn't sound if you're not in Hevy" is the top timer complaint against Hevy ([JustUseApp](https://justuseapp.com/en/app/1458862350/hevy-workout-tracker-gym-log/reviews)). The Live Activity shows exercise, set number, weight × reps, a "last time" value and the countdown with a progress bar; Musklr documents that iOS draws the card and only redraws on change, that the Lock Screen card needs iOS 16.2 and the Dynamic Island an iPhone 14 Pro or later, and that its −15/+15/skip buttons deep-link into the app ([Musklr](https://musklr.com/blog/2026/iphone-lock-screen-workout-tracking-live-activity/)); Hevy's activity additionally lets the user mark the next set complete from the Lock Screen, which requires iOS 17 interactive widgets, and it needs the user to enable Live Activities under Face ID & Passcode's "Allow Access When Locked" ([Hevy](https://www.hevyapp.com/features/live-activity/)). Strong only shipped Live Activity support in version 6.5.0 ([Strong App Store](https://apps.apple.com/us/app/strong-workout-tracker-gym-log/id464254577)), and the notes point out that a search-engine summary attributed it to 6.0.4, which the store's own history contradicts. An Apple Watch companion is not worth pursuing: it requires Swift and Xcode 16 on macOS even with `expo-apple-targets` ([expo-apple-targets](https://github.com/EvanBacon/expo-apple-targets)), watch sync is the most complained-about feature of both Strong and Hevy, and watchOS 11 already surfaces the Live Activity on the wrist.

Notes are where the personal app can beat every commercial one. Strong's Pinned Notes are the proven pattern: yellow stickies that appear each time the exercise is performed, belong to the exercise rather than the workout, are absent from history, and are explicitly meant for equipment setup ([Strong Help](https://help.strongapp.io/article/134-about-notes)); Alpha Progression markets the same pin concept specifically for machine settings ([Alpha Progression](https://alphaprogression.com/en/blog/alpha-progression-guide)), while Hevy has only routine-scoped and session notes, and its users ask for permanent ones ([Hevy Help](https://help.hevyapp.com/hc/en-us/articles/34463684392983-How-do-the-exercise-notes-routine-and-workout-notes-work); [JustUseApp](https://justuseapp.com/en/app/1458862350/hevy-workout-tracker-gym-log/reviews)). No leading tracker models machine settings as structured fields; a Trainerize feature request with 31 votes asks for exactly a "settings" section per exercise for rack heights, pulley positions and seat adjustments ([Trainerize](https://ideas.abcfitness.com/forums/167887-coach-trainer-trainerize/suggestions/40649614-have-a-setting-section-for-each-exercise)), and only a niche app stores per-machine cards with seat height and handle position ([My GymMachine Binder](https://apps.apple.com/iq/app/my-gymmachine-binder/id6756008950?l=ar)). Every open dataset flattens machines to a single "machine" or "cable" token, so the app must own this. The recommended shape keeps settings apart from the exercise definition, because the same exercise is done on different machines across gyms and one machine hosts several exercises: a `gym`, a `machine` per physical station, an append-only `machine_setting` list of key-value pairs (seat height, back pad, arm or handle position, cable height, foot plate, range limiter) with timestamps, and an `exercise_gym_pref` that resolves an exercise to a machine at the current gym. The one-arm triceps extension then carries "arm height 4" as a chip rendered inline whenever the exercise appears, with the pinned free-text note for cues that do not fit a field.

That spine is the common denominator of Hevy's API (sets with type, weight_kg, reps, distance_meters, duration_seconds, rpe), Liftosaur's history records (which uniquely carry `isUnilateral` and `completedRepsLeft` per set) and workout.cool's Prisma schema ([hevy-mcp OpenAPI copy](https://raw.githubusercontent.com/chrisdoc/hevy-mcp/main/openapi-spec.json); [Liftosaur](https://raw.githubusercontent.com/astashov/liftosaur/master/src/types.ts); [workout.cool](https://api.github.com/repos/Snouzy/workout-cool)). Copying code from wger or Liftosaur would pull the app under AGPL-3.0, whereas copying their field conventions does not; workout.cool is MIT if code reuse is ever wanted. Ivan's Push template becomes three rows: Weighted Dip (weighted_bodyweight, load_model added, 2–3 sets of 5–8, rest 180 s working and 60 s warm-up), Incline Dumbbell Press (weight_reps, per_hand, 3 sets of 8–12, 120 s), and One-Arm Cable Triceps Extension (weight_reps, unilateral_single, 3 sets of 10–15 per arm, 60–90 s, machine_id pointing at the station whose latest setting reads arm height 4). Snapshotting bodyweight onto each set at logging time is cheap insurance that historical dips keep their correct total load after the profile weight changes.

## Build it in five phases, testing the two unknowns first

The stack is Expo SDK 56 or later with TypeScript, a development build rather than Expo Go from day one (widgets and custom notification sounds both require it), `expo-sqlite` with Drizzle for storage, `expo-notifications` for the alarm, `expo-widgets` for the Live Activity, `expo-file-system` plus the share sheet for JSON export and import, and either Victory Native XL or `react-native-gifted-charts` for graphs. There is no backend, no account and no sync layer; the notes observe that most of Strong's and Hevy's reliability complaints (sets unchecking, workouts going missing, Live Sync working half the time) live in exactly the cloud and watch layers a single-user app omits ([JustUseApp](https://justuseapp.com/en/app/464254577/strong-workout-tracker-gym-log/reviews)). The ranking engine, the e1RM and volume calculators and the Strong parser are pure TypeScript modules with unit tests that run on Windows under Node, which matters because the EAS free queue can cost an hour per build: everything that can be verified without the phone should be. The notes rank effort from Windows as PWA (hours, plus a day for a push backend) below Expo with EAS (about a day for the account, credentials and first build, then minutes per change) below Capacitor or Flutter on Codemagic, below hand-rolled GitHub Actions signing, below free-ID sideloading's weekly upkeep, below anything requiring Swift; the EUR figures for EAS, Codemagic and GitHub are unpublished, and no vendor documents typical build durations, only timeouts.

Phase 0 is deliberately the riskiest work first. If `expo-widgets` cannot render a self-updating countdown, the fallback is to update the activity on each state change and rely on the notification for the alarm, which is exactly what Musklr describes iOS doing anyway ([Musklr](https://musklr.com/blog/2026/iphone-lock-screen-workout-tracking-live-activity/)); if the scheduled notification proves flaky in some trigger configuration, switching from a `TIME_INTERVAL` to a `DATE` trigger is the first thing to try given the unresolved Expo issue ([expo/expo #28027](https://github.com/expo/expo/issues/28027)). Phase 1 runs on the PC because the parser's only real unknowns, which column the `Rest Timer` rows use and whether `Note` rows exist, are answered by opening the file. Phases 2 and 3 replace Strong; Phase 4 adds what Strong never had; and the app is usable at the gym from the end of Phase 2 even if the rest is never built.

## Conclusion

The research reframes the project in two ways. First, the rest timer is not one feature among seven; it is the constraint that eliminates the free platform and decides the whole stack, because iOS will not let web code run while the phone is in a pocket, and every web-based gym app in the notes either grew a server or gave up on the pocket case. Once that is accepted, the 99 USD membership buys a stack where the hard problems (background alarms, lock-screen countdown, offline SQLite, iCloud backup) are solved by the operating system and Expo's packages rather than by Ivan, and the remaining engineering is ordinary data modelling. Second, the ranking feature, which sounds like a lookup, is the only part with real legal and statistical exposure: the one large gym-population dataset is closed by its terms, every open alternative is calibrated on competitive lifters, and the exercises Ivan actually does, belt dips aside, have thin or no standards. The right response is not to fake precision but to rank a handful of anchor lifts through a transparent, fully public formula chain, let body parts inherit through an explicit involvement matrix, and print "estimate" wherever the matrix was extended by hand.

Two smaller conclusions follow. Height turned out to be a red herring for scoring and should stay in the profile as context, while bodyweight matters more than Ivan may expect, entering both as the normaliser and as part of the load on every dip, which is why a dated bodyweight series and a per-set snapshot belong in the schema from the first migration. And the disagreements the notes surfaced, vendor copy versus user reviews on Hevy's finish prompt, two circulating versions of Poliquin's ratios, stale versus current RP landmarks, Epley versus Brzycki, are all resolvable by preferring the primary source and the more recent evidence, which is the habit the app itself should encode by storing rep counts, weights and dates next to every derived number so that any formula can be swapped later without losing history.
