# iOS platform options for a personal workout app built from Windows 10 with no Mac (research notes, 2026-09-26)

Scope: one developer on Windows 10, one iPhone, single-user app, no App Store publication. Requirements evaluated: reliable rest timer that alerts on a locked phone, offline use in a gym, local storage with backups, charts. Routes compared: (1) home-screen PWA, (2) React Native + Expo with EAS cloud builds via TestFlight or ad hoc, (3) Flutter or Capacitor/Ionic with Codemagic or GitHub Actions macOS runners, (4) sideloading (AltStore/SideStore/Sideloadly), PWABuilder, web clips. Prices are those shown on vendor pages fetched on 2026-09-26 unless marked older. Note: caniuse's tables already list "Safari on iOS 27.0" and "27.1-27.2" rows (as of 2026-09-26), so the iOS 27 line is current or imminent; none of the findings below are reported to change with it — [caniuse vibration](https://caniuse.com/vibration), [caniuse wake-lock](https://caniuse.com/wake-lock).

## Key Question 1: iOS PWA capabilities in 2026 (iOS 17/18/26) and proven rest-timer workarounds

### Takeaway
A home-screen web app on iOS 26 is the cheapest route by far (no Apple account, no build pipeline) and now has web push (iOS 16.4+), a working Screen Wake Lock in installed apps (iOS 18.4+), large storage quotas and no 7-day eviction for home-screen apps; but JavaScript is deliberately frozen whenever the app is backgrounded or the screen locks, there is no Vibration API, no client-side scheduled notification, and no background execution, so a lock-screen rest-timer alert is only achievable with a server-sent Web Push (or by keeping the screen awake with Wake Lock).

### Cited Findings

Installation and iOS 26 behaviour
- Safari 26 / iOS 26: "By default, every website added to the Home Screen opens as a web app." "There are now zero requirements for 'installability' in Safari. Users can add any site to their Home Screen." Service workers and a Web App Manifest remain optional (manifest still used for enhancements). Applies to iOS 26, iPadOS 26, macOS Tahoe, visionOS 26 — [WebKit: WebKit Features in Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- The Share > Add to Home Screen sheet in iOS 26 has an "Open as Web App" toggle, on by default; users can turn it off to keep a plain bookmark — [MacRumors how-to](https://www.macrumors.com/how-to/save-safari-bookmark-web-app-iphone-home-screen/); [heise](https://www.heise.de/en/news/iOS-26-and-iPadOS-26-Changed-web-app-behaviour-on-the-home-screen-10749652.html)
- There is no install prompt/banner API on iOS (no `beforeinstallprompt`); installation is manual via Share sheet — [firt.dev iOS PWA compatibility](https://firt.dev/notes/pwa-ios/) (page last updated 2023-06-06, so treat as older); [MagicBell guide, updated 2026-03-20](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)

Web Push and notifications
- Web Push for Home Screen web apps arrived in iOS/iPadOS 16.4 (Push API + Notifications API + Service Worker). "Web Push notifications from web apps work exactly like notifications from other apps. They show on the Lock Screen, in Notification Center, and on a paired Apple Watch." The Badging API also arrived in 16.4 — [WebKit: Web Push for Web Apps on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/); [WebKit Features in Safari 16.4](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/)
- On iOS, Web Push works only after the site is added to the Home Screen (not in the Safari tab) — [Webventures: Web Push on iOS requires installing the web app](https://webventures.rejh.nl/blog/2023/ios-web-push-requires-install/); firt.dev lists "Web Push 16.4 only for installed PWAs" — [firt.dev](https://firt.dev/notes/pwa-ios/)
- Declarative Web Push (no service worker needed to display a push) is testable on iOS 18.4/iPadOS 18.4 and works for Home Screen web apps; it still requires a server to send the push message and does not add client-side scheduling of future notifications (blog dated 2025-03-27) — [WebKit: Meet Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/)
- Notification Triggers (client-side scheduled notifications) never shipped in WebKit; "the only thing that wakes a locked phone is a push sent from a server at the deadline" (developer PR description, 2026-09-24) — [spotterai PR #39](https://github.com/Ray-Shaw06/spotterai/pull/39)
- EU caveat is obsolete: Apple's iOS 17.4 beta 2 removed Home Screen web apps in the EU, then on 2024-03-01 Apple reversed course and iOS 17.4 shipped with Home Screen web apps in the EU — [9to5Mac 2024-03-01](https://9to5mac.com/2024/03/01/apple-home-screen-web-apps-ios-17-eu/); [TechCrunch 2024-03-01](https://techcrunch.com/2024/03/01/apple-reverses-decision-about-blocking-web-apps-on-iphones-in-the-eu/). The MagicBell guide still says web push is "Not available in EU countries (iOS 17.4+)" — [MagicBell](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide); contradicted by the March 2024 reversal above.

Background execution and JS timers when locked/backgrounded
- An Apple Frameworks Engineer on the Apple forums (March 2025) confirmed JavaScript execution is intentionally halted when Safari/web content goes to the background and developers cannot override it; Apple's suggested approach for a countdown is to compute elapsed/remaining time from a stored reference date when the page returns to the foreground rather than rely on background execution — [Apple Developer Forums thread 777860](https://developer.apple.com/forums/thread/777860)
- Background Sync, Periodic Background Sync and Background Fetch are not supported on iOS — [firt.dev](https://firt.dev/notes/pwa-ios/); [MagicBell](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)
- Real-world PWA gym app issue (2026-09-24): "A locked iPhone freezes page JavaScript", and "on iOS the web view is reclaimed as soon as the app goes to the background", so a `useState`-only timer is lost; the fix plan was (1) Wake Lock (iOS 18.4+), (2) persist the timer end timestamp and resume/expire on return, (3) audible cue instead of `navigator.vibrate`, which iOS ignores — [programme-12-semaines issue #79](https://github.com/Simon0687/programme-12-semaines/issues/79)
- An old (2010-era) Apple Community thread claims JS kept running in a home-screen web app in sleep mode; this predates modern iOS and conflicts with Apple's 2025 statement above, so treat as obsolete — [Apple Community thread 2298038](https://discussions.apple.com/thread/2298038)

Screen Wake Lock
- Safari supports the Screen Wake Lock API from iOS 16.4, but "Safari on iOS 16.4 to before 18.4 was a partial implementation because it does not work in standalone Home Screen web apps, with full support coming in Safari on iOS 18.4" — [web.dev: Screen Wake Lock supported in all browsers](https://web.dev/blog/screen-wake-lock-supported-in-all-browsers); "in installed PWAs, a long-standing bug broke this API until the issue was fixed by Apple in iOS 18.4" — [Progressier Wake Lock demo](https://progressier.com/pwa-capabilities/screen-wake-lock); caniuse shows iOS Safari 16.4 through 27.x as supported with no notes — [caniuse wake-lock](https://caniuse.com/wake-lock)

Vibration
- The Vibration API (`navigator.vibrate`) is not supported in any Safari on iOS version, through 27.2 in caniuse's table — [caniuse vibration](https://caniuse.com/vibration); firt.dev also lists Vibration API as unsupported — [firt.dev](https://firt.dev/notes/pwa-ios/)

Audio when locked
- Developer report (Aug 2024): in an iOS PWA, lock-screen audio controls work until playback has been paused for ~30 seconds while locked, after which audio stops functioning until the PWA is foregrounded; no Apple response documented — [Apple Developer Forums thread 762582](https://developer.apple.com/forums/thread/762582)
- "While playing audio in Safari on iOS it is possible to minimize Safari or lock the screen and the audio continues to play, however, if the site is installed to the HomeScreen as a PWA, minimizing the PWA or locking the screen pauses the audio" — [DEV: What we learned about PWAs and audio playback](https://dev.to/prototyp/what-we-learned-about-pwas-and-audio-playback-50eh)
- A continuous silent audio file for the duration of a timer is described as a workaround to keep a session alive, but "it is not possible to start an audio session from a backgrounded state without user/server intervention"; a silent push can trigger a new session but only a server can send it — [cnasolution Q&A](https://cnasolution.com/questions/121561/ios-pwa-background-audio-support)
- A PWA timer (2026-09-23) plays its alarm through a looping HTML media element ("media bed") plus MP3 so the alarm is audible even with the Silent switch on; Safari blocked audio started from timer callbacks after the initial sound was paused; Apple's push service rejected a VAPID subject of `mailto:timer@localhost` with `403 BadJwtToken` — [wcleeah/timer PR #7](https://github.com/wcleeah/timer/pull/7)

Storage, quotas, eviction
- The 7-day cap on script-writable storage (IndexedDB, LocalStorage, SessionStorage, media keys, Service Worker registrations and cache) was introduced in iOS/iPadOS 13.4 (post dated 2020-03-24) and applies "after seven days of Safari use without user interaction on the site". "Web applications added to the home screen are not part of Safari and thus have their own counter of days of use", and first-party data deletion is not anticipated for installed web apps — [WebKit: Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)
- Storage quota since Safari 17 / iOS 17: an origin may use "up to 60% of the total disk space" in browser apps (15% in non-browser WebKit apps); "When a web app is running standalone (as Home Screen Web App on iOS ...), it has the same origin quota and overall quota as when it is opened in a browser app"; eviction is per-origin, least-recently-used; `navigator.storage.persist()` is granted by heuristics "like whether the website is opened as a Home Screen Web App" — [WebKit: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/)
- The MagicBell guide claims a "50MB storage cap" and that all cached data is gone after 7 days — [MagicBell](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide); contradicted for iOS 17+ and for home-screen apps by the two WebKit posts above.

Proven rest-timer workarounds in a PWA (developer implementations, Sept 2026)
- Server-scheduled Web Push at the deadline: the client "books" a push when a rest starts; the server stores the encrypted subscription in Upstash QStash with a Not-Before timestamp and sends the push at the deadline; cancellation on skip/finish/+15s via HMAC tokens; QStash free tier "1,000 daily publishes"; a page-alive local notification/tone still fires as fallback; "If iOS evicts the app you get the banner and the buzz, not the beeps" — [spotterai PR #39](https://github.com/Ray-Shaw06/spotterai/pull/39)
- Persist end timestamp and re-sync on `visibilitychange`; compute remaining time from a reference date on return (Apple's own suggestion) — [Apple Developer Forums thread 777860](https://developer.apple.com/forums/thread/777860); [programme-12-semaines issue #79](https://github.com/Simon0687/programme-12-semaines/issues/79)
- Keep the screen on with Wake Lock (iOS 18.4+ in installed apps) so the JS timer keeps running and an in-page sound can play — [web.dev](https://web.dev/blog/screen-wake-lock-supported-in-all-browsers); [programme-12-semaines issue #79](https://github.com/Simon0687/programme-12-semaines/issues/79)
- Another PWA gym app tracks "Sound the rest timer on the lock screen, so it can't be missed when the phone is locked" as an open problem — [formspan issue #612](https://github.com/dmytro-ch21/formspan/issues/612)

### Inferences
- For a lock-screen alert from a PWA, the only reliable mechanism is Web Push from a server; that means the "free" PWA route still needs a tiny always-on backend (a scheduler such as QStash or a cron endpoint plus web-push/VAPID keys), and it needs connectivity at the deadline, which gyms do not always have. Everything else (Wake Lock + in-page sound, timestamp resync) only works while the screen stays on or gives a late alert on unlock.
- With no Vibration API and audio paused on lock in installed PWAs, the realistic PWA UX is: Wake Lock on during the rest, audible beep while the page is visible, plus a push as the "phone in pocket" fallback.
- Offline use and local storage are no longer PWA weaknesses on iOS 17+: quota is large and installed apps are exempt from the 7-day rule; requesting `persist()` from the installed app is cheap insurance.
- iOS 26's "every site is a web app" removes install friction but nothing else changed for background execution.

### Gaps
- I found no primary Apple/WebKit statement quantifying how long a backgrounded home-screen web app keeps its in-memory state before the web view is reclaimed; only developer reports describe it as "reclaimed as soon as it goes to background".
- I found no authoritative current test (2025-2026) of whether continuous non-silent audio started in the foreground keeps playing after lock in a home-screen web app on iOS 18/26; the two reports above are from 2024 or undated.
- firt.dev's iOS compatibility page was last updated 2023-06-06, so it does not reflect iOS 17-26 changes (storage quota, Wake Lock fix, iOS 26 install changes).
- The Safari 18.4 release notes page could not be fetched (JS-rendered), so the Wake Lock fix is cited from web.dev/Progressier rather than Apple.

## Key Question 2: Expo/React Native from Windows: no-Mac build and install, prerequisites, pricing, workflow, notifications/Live Activities/background timers, storage and chart libraries

### Takeaway
A Windows-only developer can build, sign and install an Expo iOS app with EAS Build plus either TestFlight (via `eas submit`) or ad hoc internal distribution, with no Mac at any step; the hard prerequisite is the 99 USD/year Apple Developer Program, EAS's free plan (15 iOS builds/month, low-priority queue, 45-minute timeout) is enough for a personal app, and the rest timer is best implemented as a scheduled local notification (fires with the app killed) optionally upgraded to a Live Activity, which Expo SDK 56 now supports without Swift via `expo-widgets`.

### Cited Findings

Feasibility without a Mac
- "Both `eas build` and `eas submit` run on macOS, Linux, and Windows." TestFlight requires a paid Apple Developer account; `eas submit` can auto-create the App Store Connect app record; "Only an Account Holder or Admin can create the App Store Connect API key that EAS Submit uses"; internal testers: max 100, no review, available "immediately after processing"; external testers: max 10,000, Beta App Review "Required on the first build of every app version"; "Build expiry: 90 days from upload" — [Expo docs: Distribute an iOS app with TestFlight](https://docs.expo.dev/submit/testflight/)
- Ad hoc / internal distribution: "This method requires a paid Apple Developer account"; register devices with `eas device:create` (URL/QR flow captures the UDID); "that account will only be able to use this method to distribute to at most 100 iPhones per year"; EAS "provides a URL that allows them to install the app directly to their device" — [Expo docs: Internal distribution](https://docs.expo.dev/build/internal-distribution/)
- For the first iOS build you must let EAS create the distribution certificate and provisioning profile (cloud credentials); afterwards builds reuse them and can even run on GitHub Actions — [amarjanica: Submit an Expo iOS app to TestFlight using GitHub Actions](https://www.amarjanica.com/submit-expo-ios-app-to-apple-appstore/)
- Four ways to get an Expo app onto a physical iPhone (post 2024-01-27, edited 2024-03-22): Expo Go (needs a local Metro server, no Apple account, no device registration); development build (`eas build --profile development`, device registered via `eas device:create`, still needs Metro); preview/internal-distribution build; production build submitted to TestFlight/App Store — [DEV: Ways to run your Expo iOS app on a physical phone](https://dev.to/cathylai/run-an-ios-app-on-the-physical-phone-demystified-146k)
- Apple forum thread (Feb 2026, replies through Aug 2026) on building/uploading without a Mac: answers recommend GitHub Actions macOS runners with automated signing, or a cloud-Mac API; "Apple Developer Program account (required regardless of setup)" — [Apple Developer Forums thread 815497](https://developer.apple.com/forums/thread/815497)
- Ad hoc provisioning profiles are valid for one year from creation and also die when the distribution certificate or the membership expires; membership allows up to 100 devices per device type per membership year — [Apple Developer Forums thread 115245](https://forums.developer.apple.com/thread/115245); [Bitrise: Understanding provisioning for iOS applications](https://bitrise.io/blog/post/understanding-provisioning-for-ios-applications)

Apple Developer Program cost
- "The Apple Developer Program annual fee is 99 USD and the Apple Developer Enterprise Program annual fee is 299 USD, in local currency where available"; auto-renewing when enrolled via the Apple Developer app — [Apple: Program enrollment](https://developer.apple.com/help/account/membership/program-enrollment/); [Apple: Become a member](https://developer.apple.com/programs/enroll/)
- In the EU the price is presented as 99 EUR per year ("99 Euro im Jahr") — [Appaloosa blog](https://www.appaloosa.io/blog/what-is-the-apple-development-program); Apple set EU pricing to €99 in January 2015 (older) — [9to5Mac 2015-01-01](https://9to5mac.com/2015/01/01/apple-increases-ios-and-mac-developer-program-pricing-in-eu-countries-to-79e99/)

EAS pricing and limits (fetched 2026-09-26)
- Free plan: "15 Android and 15 iOS builds" per month, "Low-priority queue", "45-minute build timeout", "Send updates to 1K MAUs"; "At peak times, you may experience wait times of 90+ minutes with the low-priority queue depending on demand." Starter: "$19/month plus additional usage cost" with "$45 of build credit" and access to large workers. Per-build prices: iOS medium worker "$2", iOS large "$4", Android medium "$1", Android large "$2" — [Expo pricing](https://expo.dev/pricing); [Expo docs: plans](https://docs.expo.dev/billing/plans/)
- Free-plan builds cannot incur overages: after the 15 iOS or 15 Android builds are used, new builds wait until the next calendar month; Starter/Production/Enterprise builds use the high-priority queue with a target of zero wait — [Newly: EAS Build guide](https://newly.app/guides/eas-build); [Expo FYI: EAS Build queues](https://github.com/expo/fyi/blob/main/eas-build-queues.md)

Rest timer: local notifications, background timers, Live Activities
- Apple: "Local notifications give you a way to alert the user at times when your app might not be running. ... Your app does not need to be running for the system to deliver the notification." Triggers: `UNTimeIntervalNotificationTrigger` (after N seconds) or `UNCalendarNotificationTrigger` (date) — [Apple archive: Scheduling and Handling Local Notifications](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/SchedulingandHandlingLocalNotifications.html)
- iOS keeps only the 64 most recently scheduled pending local notifications — [flutter_local_notifications on pub.dev](https://pub.dev/packages/flutter_local_notifications)
- `expo-notifications`: `scheduleNotificationAsync` with `SchedulableTriggerInputTypes.TIME_INTERVAL` (seconds) or `DATE`; custom sounds via the config plugin `sounds` array; remote push is unavailable in Expo Go on Android from SDK 53 (development builds required); local notifications remain available in Expo Go — [Expo docs: Notifications](https://docs.expo.dev/versions/latest/sdk/notifications/)
- A 2024 Expo issue reported scheduled local notifications not arriving in the background on iOS when using `trigger: null` (immediate); it is labelled "needs more info"/"outdated" with no confirmed root cause — [expo/expo issue #28027](https://github.com/expo/expo/issues/28027)
- A PWA-vs-native comparison PR explicitly notes "Scheduled local notification (expo-notifications) fires at rest-timer-end with sound, even backgrounded/locked" — [spotterai PR #39](https://github.com/Ray-Shaw06/spotterai/pull/39)
- Expo Go "doesn't support background tasks for iOS" (personal gym-logger author, 2025-03-20) — [DEV: Building a gym logging app](https://dev.to/jjpark987/building-a-gym-logging-app-3c9c)
- Live Activities/widgets: "iOS widgets and Live Activities are stable in Expo SDK 56" (blog 2026-06-18): package `expo-widgets`, written as React components with Expo UI, "no SwiftUI required", and "Continuous Native Generation handles the Widget Extension target, the App Group configuration, and the SwiftUI scaffolding" — [Expo blog: iOS widgets and Live Activities in Expo](https://expo.dev/blog/ios-widgets-and-live-activities-in-expo); alpha shipped in SDK 55 — [Expo changelog SDK 55](https://expo.dev/changelog/sdk-55); [Expo changelog SDK 56](https://expo.dev/changelog/sdk-56)
- `expo-widgets` docs: iOS only; "not available in the Expo Go app — use development builds"; Live Activity lifecycle `start()`/`update()`/`end()`; optional APNs push updates; widget code "runs in an isolated runtime and can only use @expo/ui/swift-ui components", cannot use React hooks or async work; watchOS/CarPlay receive `bannerSmall` fallback content — [Expo docs: Widgets](https://docs.expo.dev/versions/latest/sdk/widgets/)
- Software Mansion's `expo-live-activity` (archived 2026-06-01, pointing users to `expo-widgets`) supported countdown timers ("Set as epoch time in milliseconds. This is used as an end date in a countdown timer"), elapsed timers, `timerType: 'circular' | 'digital'` in the Dynamic Island, minimum iOS 16.2, dev client required, assets max 4 KB — [software-mansion-labs/expo-live-activity](https://github.com/software-mansion-labs/expo-live-activity)
- Tutorial on building a Live Activity timer in Expo using `expo-apple-targets` — [Level Up Coding: Building a Live Activity Timer in Expo](https://levelup.gitconnected.com/building-a-live-activity-timer-in-expo-626b162f3e8d)

Storage libraries
- `expo-sqlite` + Drizzle ORM is "the smoothest path" for new Expo projects (type safety, live queries); `op-sqlite` is JSI-based, synchronous, faster for tens of thousands of rows, but "requires native builds — you can't use Expo Go"; WatermelonDB is the opinionated offline-first ORM with sync/relations — [React Native Relay: Offline-first RN 2026](https://reactnativerelay.com/article/building-offline-first-react-native-apps-2026-expo-sqlite-drizzle-orm-sync-strategies); [Kernel Daily: expo-sqlite vs op-sqlite](https://kerneldaily.com/articles/expo-sqlite-vs-op-sqlite/); [PkgPulse: Expo SQLite vs WatermelonDB vs Realm 2026](https://www.pkgpulse.com/guides/expo-sqlite-vs-watermelondb-vs-realm-react-native-local-2026); [72Technologies: Offline-first RN 2026](https://www.72technologies.com/blog/offline-first-react-native-database-2026)
- Personal-project precedents: GymLogger used SQLite for offline logging — [DEV: Building a gym logging app](https://dev.to/jjpark987/building-a-gym-logging-app-3c9c); MyoTrack used AsyncStorage — [MyoTrack on GitHub](https://github.com/Rahil16/MyoTrack)

Chart libraries
- Victory Native (XL) renders with Skia and Reanimated, "100+ FPS even on lower-end devices", but depends on `@shopify/react-native-skia`, `react-native-reanimated` and `react-native-gesture-handler`, so it needs a development build/EAS build rather than Expo Go — [React Native Relay: Victory Native tutorial](https://reactnativerelay.com/article/react-native-charts-victory-native-interactive-data-visualizations-expo); [victory-native-xl on GitHub](https://github.com/FormidableLabs/victory-native-xl)
- `react-native-gifted-charts` works without extra native modules (react-native-svg based) and is Expo Go compatible with good defaults — [PkgPulse 2026 comparison](https://www.pkgpulse.com/guides/victory-native-vs-react-native-chart-kit-vs-echarts-rn-2026); [Stackademic: Top 10 RN chart libraries 2026](https://blog.stackademic.com/my-top-10-react-native-chart-libraries-heading-into-2026-46e115e3be38)

### Inferences
- Minimal no-Mac workflow: `npx create-expo-app` on Windows -> configure `eas.json` (profile `preview` with `distribution: internal`, or `production` with `distribution: store`) -> `eas build -p ios` (EAS generates cert + profile using your Apple ID or an App Store Connect API key) -> for ad hoc: `eas device:create` once, then open the build URL on the iPhone; for TestFlight: `eas submit -p ios`, install via the TestFlight app as an internal tester. JS-only changes can go through EAS Update (1K MAU free) without consuming build quota.
- TestFlight vs ad hoc for one user: TestFlight builds expire after 90 days (must re-upload roughly 4 times a year, each a new build); ad hoc builds are tied to a profile valid up to a year and to the annual membership, so a reinstall is needed at most yearly. Either way, letting the 99 USD membership lapse eventually kills the installed app.
- Build cadence: 15 free iOS builds/month is ample for a solo app; the practical cost of "free" is queue waits (up to 90+ minutes at peak). If waits become annoying, Starter at 19 USD/month (~228 USD/year) buys the priority queue and ~22 iOS medium builds of credit.
- Rest timer design: compute the end timestamp, schedule a local notification with custom sound at that time (cancel/reschedule on skip or +15 s), and render the countdown from the timestamp when foregrounded; add a Live Activity via `expo-widgets` for a lock-screen countdown. Local notifications are limited to 64 pending, which is irrelevant for one active rest timer.
- Library choice for a solo app: `expo-sqlite` + Drizzle and `react-native-gifted-charts` (or Victory Native XL if a dev build is used anyway, which it will be for widgets/notifications).

### Gaps
- Expo's `expo-widgets` docs do not state whether a self-updating countdown (SwiftUI `Text(timerInterval:)` equivalent) is available in the JS component set; the archived `expo-live-activity` had it, `expo-widgets` may or may not. Needs a hands-on check.
- I found no authoritative figure for typical EAS iOS build duration; only the 45-minute free-plan timeout and queue-wait statements are documented.
- Expo issue #28027 leaves unresolved whether some configurations of scheduled local notifications fail in background on iOS; the documented Apple behaviour says they deliver regardless of app state.
- The Expo "latest" docs pages fetched appear to correspond to SDK 57 (URL path), but I could not confirm the current SDK number from a changelog page in this session.

## Key Question 3: Flutter and Capacitor/Ionic with cloud builds (Codemagic, GitHub Actions macOS runners) and their notification/timer options

### Takeaway
Both Flutter and Capacitor can be built and signed for iOS from Windows using Codemagic (500 free macOS M2 minutes/month, automatic code signing through the App Store Connect API) or GitHub Actions macOS runners (2,000 free minutes/month on a private repo consumed at 10x for macOS, i.e. about 200 macOS minutes; free for public repos; 0.062 USD/min beyond), both still require the 99 USD/year Apple program, and their local-notification plugins (`flutter_local_notifications`, Capacitor Local Notifications) give the same OS-scheduled rest-timer alert as Expo, while a Live Activity means writing a native Swift widget extension yourself.

### Cited Findings

Codemagic
- Free tier: "500 free macOS M2 minutes / month", Mac mini M2, 1 user, max 1 parallel build, 120-minute build duration limit; pay-as-you-go "Mac mini M2: $0.095 / minute", "Mac mini M4: $0.114 / minute", "Linux X2 and Windows: $0.045 / minute"; fixed annual team plans from "$3,990 / year" — [Codemagic pricing](https://codemagic.io/pricing/)
- Free minutes apply only to macOS M2; Linux/Windows builds have no free minutes — [Codemagic docs: Pricing](https://docs.codemagic.io/billing/pricing/)
- "With automatic code signing, Codemagic will create both the certificate and the provisioning profile on your behalf without requiring a Mac" via the App Store Connect API; "You still need to be a member of Apple Developer Program"; can create development/distribution certificates and development/Ad hoc/App Store profiles — [Codemagic blog: sign Flutter apps for iOS automatically without a Mac](https://blog.codemagic.io/automatic-code-signing-for-ios-that-doesnt-require-a-mac/); [Codemagic docs: iOS code signing](https://docs.codemagic.io/flutter-code-signing/ios-code-signing/)
- Ionic/Capacitor on Codemagic: `codemagic.yaml`, App Store Connect API key (Issuer ID, Key ID, .p8), `distribution_type: ad_hoc` or `app_store`, `submit_to_testflight: true`, built on `mac_mini_m2` instances — [Codemagic docs: Building an Ionic app](https://docs.codemagic.io/yaml-quick-start/building-an-ionic-app/)

GitHub Actions

- Cost per year for a solo Flutter/Capacitor developer: 99 USD Apple + 0 USD Codemagic (500 M2 minutes covers roughly 25-50 iOS builds if a build takes 10-20 minutes; that duration is my estimate, not sourced) or 0 USD GitHub Actions if the repo is public (or ~200 macOS minutes/month if private).

- Capacitor is attractive if the PWA route is tried first: the same web code can later be wrapped to gain OS local notifications and Live Activities, at the cost of the full Apple/CI setup.
- Compared with Expo, Flutter/Capacitor have no equivalent of `expo-widgets` (JS-defined Live Activity), so a lock-screen countdown needs Swift, which is awkward to write and debug without Xcode.

## Key Question 4: Sideloading and free provisioning (free Apple ID, AltStore/SideStore/Sideloadly on Windows), plus PWABuilder and web clips

### Takeaway
A free Apple ID can sign an app for only 7 days and only 3 apps at a time (10 app IDs per week), so for a daily-use personal app the free route means AltStore (needs AltServer running on the Windows PC on the same Wi-Fi to refresh), SideStore (computer only for setup, then self-refreshes through an on-device VPN), or Sideloadly (desktop daemon auto-refreshes); all require the non-Microsoft-Store iTunes and iCloud on Windows and an .ipa you still have to build in the cloud, so they add maintenance rather than remove the need for a build pipeline; PWABuilder's iOS package is an Xcode project meant for the App Store and web clips are just the PWA route.

### Cited Findings

Free Apple ID limits
- "If using a free Apple Account, SideStore can only install 3 apps (including itself) at a time. Additionally, only 10 different apps may be installed in a week." "To remove this restriction (and also get a 365 day expiry), you can pay for a $99/year Apple Developer account." SideStore "will periodically 'refresh' your apps in the background, to keep their normal 7-day development period from expiring" — [SideStore FAQ](https://docs.sidestore.io/docs/faq)
- Sideloadly: with a free account sideloaded apps remain valid for seven days; an auto-refresh daemon re-signs them; a 99 USD/year developer account "extends app validity to 1 year and allows more simultaneous app installations"; supports Windows 7+ and macOS 10.12+, iOS 7 through 26+; free (Patreon-funded); Wi-Fi sideloading supported — [Sideloadly](https://sideloadly.io/)
- AltStore uses Apple's free-developer signing to install up to three apps that expire every 7 days and are refreshed automatically; "To refresh before the week runs out, AltServer has to be running on a computer on the same Wi-Fi" — [XDA: How to sideload apps on any iPhone using AltStore](https://www.xda-developers.com/how-to-sideload-apps-iphone-altstore/); [builds.io comparison](https://builds.io/blog/technologies/ios-technologies/sideloadly-vs-altstore-vs-sidestore/)

Windows requirements
- AltServer for Windows requires iTunes and iCloud installed directly from Apple's website, not the Microsoft Store versions; Store versions must be uninstalled first (an alternate workaround exists in the troubleshooting guide) — [AltStore FAQ: How to install (Windows)](https://faq.altstore.io/altstore-classic/how-to-install-altstore-windows); [AltStore troubleshooting guide](https://faq.altstore.io/altstore-classic/troubleshooting-guide)
- SideStore "is a fork of AltStore that doesn't require an AltServer": a computer is used once for initial setup, then installs/refreshes are computer-free — [SideStore on GitHub](https://github.com/SideStore/SideStore). Setup on Windows needs the non-Microsoft-Store iTunes/iCloud, a pairing file generated on the PC (e.g. jitterbugpair / idevice_pair) and transferred to the phone, and a WireGuard/StosVPN profile that must be on whenever installing, updating or refreshing — [SideStore docs: Prerequisites](https://docs.sidestore.io/docs/installation/prerequisites); [SideStore docs: Install](https://docs.sidestore.io/docs/installation/install); [SideStore docs: Pairing file](https://docs.sidestore.io/docs/advanced/pairing-file); [jkcoxson/idevice_pair](https://github.com/jkcoxson/idevice_pair)

Other routes
- PWABuilder's iOS platform generates a Swift app hosting the PWA in a WKWebView "producing a zip file containing an Xcode project that you can compile on your Mac and publish to the App Store"; Xcode is required to build (open the `.xcworkspace`) — [PWABuilder blog: Publish your PWA to the iOS App Store](https://blog.pwabuilder.com/posts/publish-your-pwa-to-the-ios-app-store/); [pwa-builder/pwabuilder-ios](https://github.com/pwa-builder/pwabuilder-ios)
- Web clips: iOS 26 makes every Home Screen shortcut a web app by default, so a "web clip" is functionally the PWA route — [WebKit Features in Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- Expo's own docs state ad hoc/internal distribution "requires a paid Apple Developer account" — [Expo docs: Internal distribution](https://docs.expo.dev/build/internal-distribution/)

### Inferences
- Free-ID sideloading only solves signing; the .ipa must still come from EAS/Codemagic/GitHub Actions, and EAS/Codemagic signing flows assume a paid account. Producing an unsigned or free-team-signed .ipa in the cloud for AltStore is possible in principle but is not documented by these vendors, so expect manual fastlane/xcodebuild work.
- Daily-use realism: with the free ID the app stops opening after 7 days unless refreshed; AltStore/Sideloadly need the Windows PC awake and on the same Wi-Fi, SideStore needs a VPN toggle and sometimes re-pairing after iOS updates. For a gym app used several times a week, a missed refresh means no timer at the gym. Paying 99 USD removes the 7-day/3-app limits for all three tools, at which point EAS ad hoc or TestFlight is simpler.
- PWABuilder without a Mac only works if the generated Xcode project is built on a cloud Mac (Codemagic/GitHub Actions), which is the same effort as a Capacitor project with fewer plugins.

### Gaps
- The AltStore FAQ index page fetched had no body text; AltStore's Windows requirements are cited from its install page title/summary and XDA, not verbatim.
- I did not verify whether SideStore/AltStore currently work on iOS 26 (Sideloadly claims "iOS 7 — 26+").
- AltStore PAL (EU alternative marketplace) requires Apple notarization and developer-program terms; I did not research whether it offers a practical path for a single personal app.

## Key Question 5: Apple Watch companion or Live Activity for the rest timer: what each route requires

### Takeaway
A Live Activity (iOS 16.1+) is the practical lock-screen/Dynamic-Island countdown and, since watchOS 11, it also appears automatically in the Apple Watch Smart Stack without a watch app; Expo can produce one without Swift via `expo-widgets` (SDK 56+) built on EAS, Flutter/Capacitor need a hand-written ActivityKit widget extension, a PWA cannot do it at all (its push notifications do show on a paired Watch), and a true watchOS companion app requires Swift/SwiftUI and, for `expo-apple-targets`, Xcode 16 on macOS 15.

### Cited Findings
- Apple ActivityKit: Live Activities require iOS 16.1+, can run up to 8 hours and remain on the Lock Screen up to 4 more hours, countdowns use `Text(timerInterval:)`, and Live Activities appear on Apple Watch (watchOS 11 Smart Stack) automatically without a dedicated watch app — [Apple: Displaying live data with Live Activities](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)
- Expo SDK 56: Live Activities and widgets as React components, "no SwiftUI required", extension target and App Group generated by CNG (blog 2026-06-18) — [Expo blog](https://expo.dev/blog/ios-widgets-and-live-activities-in-expo); `expo-widgets` requires a development build (not Expo Go); watchOS gets `bannerSmall` fallback content — [Expo docs: Widgets](https://docs.expo.dev/versions/latest/sdk/widgets/)
- `expo-apple-targets` supports "widget, watch, watch-widget, clip, ..." targets; "watch" is a Watch App with companion iOS app; targets are written in Swift/SwiftUI; requirements "CocoaPods 1.16.2 (ruby 3.2.0), Xcode 16 (macOS 15 Sequoia), and Expo SDK +53"; "The codesigning is theoretically handled entirely by EAS Build" — [EvanBacon/expo-apple-targets](https://github.com/EvanBacon/expo-apple-targets); "Watch apps must be built in pure Swift/SwiftUI. React Native does not support watchOS" — [Medium: How to build an Apple Watch app with Expo](https://chethiyakd.medium.com/how-to-build-an-apple-watch-app-with-expo-b254ea3aec6c)
- Flutter: a Live Activity needs "a native iOS widget extension" with ActivityKit — [heart-of-yours issue #133](https://github.com/kit-g/heart-of-yours/issues/133)
- PWA: Web Push notifications from home-screen web apps "show on the Lock Screen, in Notification Center, and on a paired Apple Watch" — [WebKit: Web Push for Web Apps](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
- Commercial precedent: Restrr (gym rest timer) advertises Live Activities/Dynamic Island for the timer — [Restrr on the App Store](https://apps.apple.com/us/app/restrr-gym-rest-timer/id6478751420); Hevy's lock-screen timer is cited as a switching reason by users of another tracker — [heart-of-yours issue #133](https://github.com/kit-g/heart-of-yours/issues/133)

### Inferences
- For a no-Mac developer, "Live Activity via `expo-widgets`" is the only lock-screen countdown route that does not require writing or debugging Swift; combined with a scheduled local notification (sound at the end) it covers the "phone locked in pocket" case and the "glance at lock screen" case. It also puts the countdown on an Apple Watch running watchOS 11+ for free.
- A dedicated watchOS companion app is not realistic without a Mac: even with `expo-apple-targets` handling signing on EAS, authoring and testing SwiftUI without Xcode is impractical.

### Gaps
- Whether `expo-widgets` can render a self-updating countdown without pushing updates every second (the SwiftUI `timerInterval` equivalent) is not documented in the fetched page; must be tested.
- I found no report of someone building an `expo-apple-targets` watch target entirely from Windows via EAS.

## Key Question 6: Data safety: backing up local-only app data on iOS for a single user

### Takeaway
For a native app the simplest safety net is Apple's own iCloud Backup (it includes app data that is not otherwise synced, so a SQLite file in the app's Documents directory rides along), plus an explicit "Export JSON" share-sheet action to Files/iCloud Drive; for a PWA the data lives in Safari-managed IndexedDB, which is protected from 7-day eviction when installed and can request `persist()`, but the only user-controlled backup is an export/import file feature.

### Cited Findings
- "iCloud backups include all the information and settings stored on your device that don't already sync to iCloud", excluding data already synced (Notes, iCloud Photos, Messages in iCloud, etc.) (page dated 2025-02-25) — [Apple Support: What does iCloud Backup include](https://support.apple.com/en-us/108771)
- SQLite in WAL mode consists of `.sqlite`, `.sqlite-shm` and `.sqlite-wal` files; after a device restore the `-wal` file may be missing and the database may not open, so developers checkpoint or copy the DB properly before backup — [Apple Developer Forums thread 704859](https://developer.apple.com/forums/thread/704859); [Apple Developer Forums thread 765552 (Flutter SQLite to iCloud)](https://developer.apple.com/forums/thread/765552)
- `expo-sqlite` restore recipe: place the backup file in `${FileSystem.documentDirectory}SQLite/` before opening the database — [expo/expo issue #8109](https://github.com/expo/expo/issues/8109)
- iCloud Drive file API for Expo (create folders, upload/download files, "JSON exports, app-generated archives, and manual backup or restore flows", SQLite backup recipes) — [@oleg_svetlichnyi/expo-icloud-storage on npm](https://www.npmjs.com/package/@oleg_svetlichnyi/expo-icloud-storage?activeTab=readme)
- iCloud key-value store wrappers for Expo (`NSUbiquitousKeyValueStore`), suitable for small settings; the whole store is capped at 1 MB / 1024 keys per app — [okwasniewski/expo-icloud-storage](https://github.com/okwasniewski/expo-icloud-storage); [TheNaubit/expo-cloud-settings](https://github.com/TheNaubit/expo-cloud-settings); [@oleg_svetlichnyi/expo-icloud-storage](https://www.npmjs.com/package/@oleg_svetlichnyi/expo-icloud-storage?activeTab=readme)
- PWA storage: installed web apps have their own days-of-use counter (no 7-day purge), quota up to 60% of disk, and `navigator.storage.persist()` is granted heuristically for Home Screen web apps — [WebKit: Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/); [WebKit: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/)
- Personal-project precedent: a SwiftUI workout logger stores workouts as a plain-text file and pushes entries to GitHub as its backup (search summary) — [GitHub topic: fitness (Swift)](https://github.com/topics/fitness?l=swift&o=desc&s=updated&utf8=%E2%9C%93)

### Inferences
- Simplest for one user on a native build: keep data in SQLite under Documents (backed up by iCloud Backup automatically), add a one-tap "Export JSON/CSV" via the iOS share sheet (Files, iCloud Drive, AirDrop, email) and an "Import" picker; optionally auto-write a JSON snapshot to iCloud Drive after each workout. Avoid `NSUbiquitousKeyValueStore` for workout history (1 MB cap).
- For the PWA: keep data in IndexedDB, call `persist()` on first run, and implement export/import (download/upload JSON) because Safari-managed storage is not part of a user-visible backup and clearing website data deletes it.
- Deleting the app (native) or removing the home-screen icon (PWA) deletes local data; only exported files or iCloud Backup survive that.

### Gaps
- Apple's support page does not explicitly enumerate "app data" as an item; the inclusion of app Documents in iCloud Backup is inferred from the "everything not already synced" wording plus the SQLite/WAL restore threads.
- I found no source on whether iOS includes a home-screen web app's IndexedDB in iCloud Backup or device-to-device transfer.
